### 1.2 PostgreSQL и Redis — отдельно от файлов (обязательное разделение)

| | PostgreSQL | Redis |
|---|---|---|
| Том | `animastor_pg-data` (именованный) | `animastor_redis-data` (именованный) |
| Расположение на хосте | `/var/lib/docker/volumes/animastor_pg-data/_data` | `/var/lib/docker/volumes/animastor_redis-data/_data` |

| `backups/` | архивы, дампы | иначе бэкап данных попадёт внутрь бэкапа → рекурсия и порча манифестов |
| `db/` | PG/Redis файловые тома | **другая** процедура восстановления (§1.2); перенос только вместе с остановкой записи |

## 4. Этап 4. Требования к переносимости внешнего хранилища

### 4.1 Единый способ определения хранилища
1. **Хост-сторона:** одна переменная `DATA_ROOT` (в `.env`, вносит владелец) **или** один именованный
   том Docker на раздел данных. Запрет на абсолютные пути к монорепо в compose-файлах.
2. **Контейнерная сторона:** единственный источник — `runtime-config.js` (`BOOKS_DIR`, `OUTPUT_DIR`).
   Проверка на отсутствие второго источника: **запретить литералы** `'/data/*'` вне `runtime-config.js`
   (сейчас нарушено в D13/D14 — 4 места).
3. Существующие порты уже готовы: `configureBooksRoot()` (vbook) и binding `artifactRoot`
   (orchestration) — **использовать их**, не добавлять новые механизмы.
4. **Никаких платных/сторонних сервисов не выбирается** — выбор NFS/SMB/S3/локального диска
   **только решением владельца** (N1).

### 4.2 Стабильные идентификаторы и ссылки из БД
- Идентичность артефакта = составляющие **уже сейчас**: `book_id` + `build_id` + `chapter_id` + `scene_id`
  + грамматика имён (`generation/artifact-naming.js` — единственный владелец имён файлов). **Путь не является идентификатором.**
- В БД хранить **относительный** путь от корня хранилища (`build_x/имя_файла`), абсолютный путь —
  вычислять в момент чтения из `OUTPUT_DIR`. Это снимает D12/D25.
- `image_units.scene_audio_file` (только имя файла) и `output_manifests.build_id` — переносимы как есть.

### 4.3 Поддержка локального каталога сейчас и сетевого/объектного в будущем
| Требование | Сейчас | Что нужно для сетевого/объектного |
|---|---|---|
| Локальный каталог | ✅ работает | — |
| Именованный том/Docker volume | не используется для data (bind-mount) | перевести mount на том с `driver_opts.device` (P2-альтернатива) |

| Сетевая ФС (NFS/SMB) | ❌ не проверялась | проверить семантику `rename` и блокировок: аудио/видео используют `rename` как атомарный коммит (10+ мест), **book.json — нет** → на NFS сначала устранить неатомарную запись (N3/N7) |

### 4.4 Контроль целостности и проверка полноты миграции
1. **Манифест до:** `sha256sum` всех 156 файлов + `inventory.txt` (путь, размер, mtime, uid/gid).
2. **Манифест после:** тот же алгоритм над целевым каталогом → `diff` пуст.
3. **Счётчики:** `find -type f | wc -l` = 61 / 95; `du -sb` = 1 703 724 / 63 203 425.
4. **Связь с БД:** каждый непустой `scene_assets.path` → файл существует (сейчас 25/26; битый путь
   `build_b1` зафиксировать как известное расхождение и не «лечить» на этом этапе).
5. **Глубокая выборка:** ≥10 файлов `output` и **все** `books` — побайтовое сравнение.
6. **После переключения mount:** повтор п.1–3 из контейнера (`docker exec … sha256sum`).
7. **Критерий PASS:** 0 расхождений манифестов + P3-проверки зелёные. **Любое расхождение → откат.**

### 4.5 Политика резервирования и восстановления (предложение к утверждению N2/N10)
| Данные | Средство | Частота (предложение) | Проверка |
|---|---|---|---|
| `data/books` | `tar`/`rsync` + `manifest.sha256` в `data/backups/app/` | ежедневно (данные малы, пишутся часто) | мок-restore в scratch + `sha256sum -c` |
| `data/output` | тот же архив либо периодическая синхронизация; **сейчас исключён из бэкапа — исключение снять** | ежедневно/еженедельно по объёму | выборка 10 файлов |
| PostgreSQL | `pg_dump -Fc` + `--schema-only` | ежедневно | `pg_restore --list` = 0 ошибок; тестовое восстановление в изолированную БД |
| Redis | `BGSAVE` → копия RDB | ежедневно (+ перед каждой миграцией) | `redis-check-rdb` |
| Резервные копии | отдельный каталог/диск, **не внутри бэкапируемого дерева** | — | `gzip -t`, `sha256sum -c` |
| Расписание | **сейчас crontab пуст, запуски вручную (последний полный — 08.10)** | решение владельца N10 | — |

**Восстановление:** документировать два разных runbook — «файловые данные» (распаковка + сверка манифеста)
и «БД» (`pg_restore` при остановленном backend; Redis — замена RDB при остановленном Redis **и** backend).
Восстановление БД из копии 12.10 при живой генерации рассинхронизирует локи/leases → **всегда окно**.

### 4.6 Разделение постоянных данных и временных результатов
- Постоянное: `persistent/` (книги), `generated/` (артефакты, пока требуемые пользователю), `db/`.
- Временное: `temp/` (никогда не монтировать на сетевую ФС), контейнерный `/tmp`, `*.tmp`-стражи,
  кэш осциллограмм, ComfyUI `temp/`/`output/` на GPU-хосте.
- Политика: временные каталоги **не входят** в манифесты и **не бэкапятся**; их отсутствие после
  восстановления не является ошибкой.
- Рекомендация: `generated/` в перспективе можно считать **воспроизводимым** (регенерация),
  но до подтверждения владельца он бэкапится наравне с `persistent/` (N11).
