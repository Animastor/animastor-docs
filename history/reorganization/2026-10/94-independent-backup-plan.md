### 1.2 Варианты

#### A. Второй блочный том у провайдера (attach к этой же VM) — рекомендуемый базовый вариант
- **Доступный объём:** 0 (том не подключён). Целевой: **не менее 100 GB** (см. математику
  §3.3: ~1.5–3 GB на год при текущих объёмах + запас на рост `data/output`, который сейчас
  63.2 MB и растёт с каждой генерацией).
- **Доступ и шифрование:** подключение через панель провайдера (нужны учётки владельца);
  появляется `/dev/sdb` → `cryptsetup` (есть в системе) — LUKS2 с passphrase, который хранит
  только владелец, либо незашифрованный ext4. Монтирование — root (у `animastor` sudo нет →
  либо выдать разовый доступ, либо автоматизацию вести от root).
- **Проверка SHA-256:** полностью возможна — манифест копируется вместе с данными,
  `sha256sum -c` на целевом томе; для rsync — `rsync -c`/`--checksum` для контроля.
- **Восстановление:** `rsync -a` обратно или `tar -x` с `--numeric-owner`; том читается
  любым спасательным окружением.
- **Риски/стоимость:** риск потери доступа — низкий (нужен только вход в панель провайдера,
  passphrase LUKS хранится у владельца); но том лежит **в том же дата-центре/на том же
  хосте**, что и источник → не защищает от отказа провайдера/учётной записи. Стоимость —
  тариф провайдера (спросить; в анализе не используется).

#### B. Удалённый SSH-сервер/VPS (push с этой машины) — рекомендуемый офсайт-вариант
- **Доступный объём:** 0 (цель не выделена). Объём определяется сторонним сервером
  (рекомендуем ≥ 50 GB при текущем наборе ~90 MB/копия).
- **Доступ и шифрование:** нужны `host`, `port`, пользователь и **приватный ключ** —
  сгенерировать ed25519 на этой машине и передать владельцу публичную часть для
  `authorized_keys` (приватный ключ хранить mode 600, не в репозитории). Транспорт — SSH
  (шифруется); при необходимости — предварительное шифрование архива: `openssl enc -aes-256-gcm`
  (есть) или `gpg --symmetric` (есть, ключи не нужны) — passphrase у владельца.
  **Не использовать** пароль по SSH/`rsync` по plaintext и не хранить ключ в Git.
- **Проверка SHA-256:** манифест передаётся вместе с копией, контроль выполняется
  **на удалённой стороне** (`ssh host 'sha256sum -c …'`); дополнительно периодическая
  обратная сверка (`rsync -c`).
- **Восстановление:** `rsync -a host:… /home/animastor/…` + `sha256sum -c`; для PG — `pg_restore`
  из скачанного дампа, для Redis — `redis-check-rdb` + изолированная загрузка (проверено в Stage 93).
- **Риски/стоимость:** потеря ключа = потеря доступа (держать резервную копию ключа у владельца);
  утечка ключа = доступ к бэкапам (ключ только для одной цели, с ограничением `command=`/`no-agent-forwarding`);
  зависимость от исходящего трафика (сейчас работает); стоимость — тариф стороннего сервера
  (не определялся). Инструменты `rsync`/`ssh` **уже установлены** — установка не нужна.

#### C. S3-совместимое объектное хранилище
- **Доступный объём:** 0 (нет учётных данных и инструмента). Объём провайдерский.
- **Доступ и шифрование:** нужны `endpoint`/`bucket`/`access_key`/`secret_key` от владельца;
  TLS в транспорте; опционально SSE провайдера либо клиентское шифрование `openssl`/`gpg`.
  **Требуется установка** клиента (`rclone` или `awscli`) → изменение системы (нужно
  согласование: `apt`/бинарник, запуск от root), в рамках этапа **не устанавливалось**.
- **Проверка SHA-256:** манифест загружается рядом с объектами; сверка скачиванием
  (`rclone check` / `aws s3 cp` + `sha256sum -c`); в клиентах есть `--checksum`.
- **Восстановление:** скачивание + проверка + распаковка; версионирование бакета даёт
  «бесплатное» историческое хранение.
- **Риски/стоимость:** утечка ключей = доступ ко всем бэкапам (роли/отдельный ключ только на
  запись в один bucket); стоимость — объём + исходящий трафик (только при восстановлении);
  зависимость от провайдера; риск блокировки доступа при компрометации аккаунта.

#### D. NAS/SMB/NFS в локальной сети
- **Доступный объём:** 0 (ни адреса, ни точки монтирования). 
- **Доступ и шифрование:** нужен адрес + учётные данные; **клиентов нет** (`mount.cifs`,
  `mount.nfs` отсутствуют) → требуется установка пакета (согласование) и запись в `/etc/fstab`
  (root). Шифрование — только если сторона поддерживает (SMB3-encrypt/Kerberos), иначе
  «в локалке без шифрования» — приемлемо только в доверенном контуре.
- **Проверка SHA-256:** возможна на смонтированной точке (`sha256sum -c`).
- **Восстановление:** монтирование + `tar -x`/`rsync -a`.
- **Риски/стоимость:** потеря сети/NAS = потеря доступа; credentials хранятся в `/etc/fstab`
  (root-only) или keyfile (mode 600); стоимость — оборудование/подписка NAS.

#### E. Физический/переносной носитель (USB) — практически неприменим
- **Доступный объём:** 0. Виртуальная машина (KVM) **не имеет USB-устройств** (`lsblk` их
  не показывает), т.е. носитель можно только подключить из панели провайдера как диск
  (тогда это вариант A) либо выгружать данные вручную.
- **Проверка SHA-256 / восстановление:** теоретически те же `sha256sum`/`tar`, но без
  автоматизации.
- **Риски/стоимость:** только ручной перенос, риск потери/порчи носителя, нет регулярности.
  Использовать только как разовый резервный экспорт по решению владельца.

#### Дополнение (не замена): снапшот диска у провайдера
Дешёвый третий уровень защиты (блок-снапшот `sda2`), но: снимок **на том же хранилище**
(не спасает от отказа провайдера/аккаунта), снимок **не приложим к файлам напрямую**
(только восстановление тома), не даёт пофайлового контроля SHA-256. Годится только как
дополнение к A/B/C.

### 1.3 Решение по §1

**Копия на этот же диск и в `~/backups` независимым хранилищем не считается и не создавалась.**
Ожидается решение владельца (§5, D1): выбор из A–E, объём, учётные данные/ключ, инструмент

### 2.2 Почему не попали в каталог (проверенная цепочка)

1. **Создание идёт только на диск.** `POST /api/v1/book/blank`
   (`packages/animastor-editor/src/entity-crud-routes.cjs:671`) формирует id через
   `generateBookId('Новая книга')` → `новая_книга_<Date.now()>()
   (`packages/animastor-vbook-runtime/src/lazy-book/paths.js:27`) и вызывает
   `editorModel.commit(...)` — то есть пишет файлы в `BOOKS_DIR`.
2. **Строка в `books` создаётся не в самом роуте, а косвенно**: роут вызывает
   `editorPorts.resolveOwnership(...)` (там же, :722), при ошибке лишь пишет
   `[CREATE BLANK BOOK] Ownership attach failed … (non-fatal)` и **продолжает**.
   `resolveWorkspaceForBook` (`backend/src/middleware/workspace-ownership.js:57`) создаёт
   строку через `bookRepo.ensureBook(...)` **только если** нашёл рабочий воркспейс.
3. **Для 5 книг вызова ownership в коде ещё не было.** `git log -S'resolveOwnership'` по
   `entity-crud-routes.cjs` → коммит `92577b5d` от **2026-09-08**. Книги, созданные **07.09**
   (5 шт., позиции 1–5), создавались раньше появления этой логики → строка в `books`
   не могла появиться в принципе.
4. **Для 3 книг (14.09, 10.10 ×2) логика уже существовала, но строк всё равно нет** —
   значит, в момент создания `resolveOwnership` завершился ошибкой/нулём (напрямую
   подтвердить нельзя: логи контейнера доступны только за последние 33 ч, старые ротации
   недоступны без root). Путь исключён из анализа **не был**: `developer` + его personal
   workspace (`Developer Workspace`) существуют и сейчас, `ensureBook` корректен
   (`book-repo.js:5`), т.е. при исправной работе кода строка появилась бы. → это открытый
   вопрос (§5, D6).
5. **Следствие в проде:** 
   - PostgreSQL: **0 строк** в `books`/`book_source`/`book_snapshots`/`scenes`/
     `generation_tasks`/… — проверены все **24 таблицы** с колонкой `book_id`
     (по `book_id` там только `ba_…`, `import_…`, `orphan_book` и `wspai-…-chatbook`).
   - Логи при каждом обращении: `[BOOK-RECOVER] … skipped — book not registered (no books row)`.
   - Каталог `GET /api/v1/books` (анонимно, без workspace): показывает **ровно эти 8 книг**
     (`source_type: disk`, `workspace_id: null`) и **не показывает** зарегистрированные
     `ba_…`/`import_…` — потому что анонимам отдаются только книги без владельца
     (`recent-books-routes.cjs`, ветка `else { … filter(entry => !entry.workspace_id) }`).

### 3.3 Retention (математика от измеренных объёмов)

Измерено: полный набор **88.3 MB**; свободно **19 701 125 120 Б**.

Вариант «всё по-крупному, tar-копии»:
- 7 ежедневных × 88.3 MB ≈ **618 MB**
- 4 еженедельных × 88.3 MB ≈ **353 MB**
- 6 ежемесячных × 88.3 MB ≈ **530 MB**
- **Итого ≈ 1.50 GB (7.6 % свободного места)** — при условии, что `output` не вырастет.

Рекомендуемый вариант — **инкремент с hardlink** (`rsync -a --link-dest=…`, ext4 поддерживает
hardlink, `rsync` установлен): ежедневная копия занимает только **изменённые** файлы;
плюс ежедневный `pg_dump` (0.43 MB) и Redis-RDB (25.9 MB) как отдельные файлы:
- ежедневная прибавка ≈ **26.3 MB + дельта `output`**;
- retention 14 ежедневных / 8 еженедельных / 6 ежемесячных → **≈ 1.0–1.6 GB на год** при
  текущем `output`; при росте `output` до 500 MB — **≈ 6–8 GB** (упирается в 18.35 GiB).

**Лимит (предложение):** каталог резервных копий — не более **10 GB**; при превышении —
**только уведомление**, автоматического удаления нет (запрет этапа; удаление — отдельное
согласованное решение D5).

### 3.4 Окно трафика для файловой копии

Замер по proxy-логам за 33 ч: 17 850 запросов, **ноль «тихих» часов** (минимум ≈ 140/ч,
максимум ≈ 1 666/ч; пики 19.10 23:00 и 20.10 01:00 UTC). Самые слабые часы в выборке:
12:00 (171), 14:00 (140), 06:00–07:00 (157).
→ Предложение: ставить 15–30-секундное окно в **12:15 UTC**, но **перед фиксацией расписания
собрать статистику за 1–2 недели** (решение D3) — одной выборки в 33 ч недостаточно.

### 3.5 Как получить согласованную копию при активной записи

Явно фиксируем (по указанию владельца): **двойная сверка за ~6 минут, сделанная в Stage 93,
НЕ является гарантией атомарного снимка.** Это только индикация простоя. Гарантия возможна
тремя способами:

- **W1. Короткое окно обслуживания (единственная гарантия на текущем коде).**
  Алгоритм: `docker stop animastor-backend` (пишет файлы `books`/`output`) →
  `tar` каталогов → `docker start animastor-backend`; PG и Redis **не останавливать**
  (их снимки консистентны независимо). Ожидаемая длительность окна: 15–30 с (64.9 MB чтения).
  Ограничения: требует согласования (Stage 93 запрещал остановку сервисов), кратковременно
  недоступны редактор/плеер; авторизация/прокси не трогаются.
  Кросс-компонентная согласованность (файлы ↔ output ↔ БД ↔ Redis) достигается **только** здесь.

- **W2. Атомарная запись в коде (устраняет причину).**
  Писать `book.json`/главы через temp-файл + `fsync` + `rename` — тогда одиночное чтение
  во время записи всегда даёт либо старую, либо новую версию файла. Требует отдельного этапа
  (правка кода + тесты) и **не** даёт согласованности *между* файлами одной книги.

- **W3. Снапшот ФС (LVM/btrfs/ZFS).** На текущей раскладке **недоступен**: `sda2` — обычный
  раздел ext4 без LVM/сабволюмов. Реализация = деструктивная миграция, вне рамок этапа.

- **W4. Принять компромисс (текущее состояние).** Копировать без окна, документируя риск
  «файл мог быть записан частично»; компоненты PG/Redis при этом всё равно согласованы.
  Приемлемо только как временное положение до D2.

Рекомендация: **W1 для регулярного расписания** (короткое ежесуточное окно) либо **W2 как
инженерное исправление** (тогда окно не нужно вовсе); W3 — не предлагается; W4 — только с
явной отметкой риска в отчёте.

### 3.6 Контроль ошибок, уведомления, проверка восстановления, защита от переполнения

**Контроль ошибок (проект скрипта `backup-run.sh`):**
- `set -euo pipefail`, `trap 'on_error $LINENO' ERR`, каждый шаг пишет код возврата в лог
  `~/backups/logs/backup-YYYY-MM-DD.log`;
- после каждой копии — **обязательная проверка**: `gzip -t` + `tar -tzf` (счёт файлов),
  `sha256sum -c manifest`, `pg_restore --list` (счёт TOC), `redis-check-rdb` (счёт ключей);
- сверка с источником: число файлов и `sha256` источника до/после (в Stage 93 — pass1/pass2);
- сверка с прошлым успешным запуском (детект «внезапно 0 файлов» / пустого дампа);
- при любом отклонении — **выход с ненулевым кодом** (никогда не «проглотить» ошибку).

**Уведомление о сбое:** MTA в системе **нет** (`mail/sendmail/msmtp` отсутствуют). Варианты:
1. **webhook** (рекомендуемый): `curl -fsS -X POST <URL от владельца> …` с результатом запуска
   и размерами; `curl` уже установлен; нужно согласовать URL/токен (D3);
2. e-mail через внешний SMTP → требует установки `msmtp` (согласование) + учётки;
3. `systemd`-таймер с `OnFailure=` (требует root для установки unit) — уведомление уходит в
   journald/агент мониторинга;
4. минимум без внешних зависимостей: файл-статус `~/backups/logs/LAST_STATUS` (для дашборда)
   + лог, но **не оповещает** — считать только вспомогательным.

**Проверка восстановления (drill):**
- **ежедневно (авто):** `gzip -t`, `tar -tzf`, `sha256sum -c`, `pg_restore --list`,
  `redis-check-rdb` — без записи в production;
- **еженедельно (авто):** распаковка последней копии в изолированный scratch + `sha256sum -c`
  по манифесту источника, затем удаление scratch (как в Stage 93);
- **ежемесячно (авто, без воздействия на production):** запуск **эфемерного** контейнера
  `postgres:16` (`--rm`, том на tmpfs/scratch), `pg_restore` туда, сверка числа таблиц/строк
  с источником, удаление контейнера; аналогично `redis:7` для RDB. **Не** трогает
  `animastor-pg`/`animastor-redis` и не требует окна (в отличие от восстановления *в*
  production);
- **ежеквартально (согласование):** реальное восстановление в production — только с окном и
  прямым решением владельца.

**Защита от переполнения диска:**
- **preflight** перед каждым запуском: свободно ≥ `max(5 GB, 5 × размер набора)`; иначе —
  **пропуск + уведомление** (не удалять ничего автоматически);
- контроль размера каталога бэкапов (лимит 10 GB → уведомление, не удаление);
- мониторинг роста `data/output` (сейчас 63.2 MB) как основного драйвера;
- `df`-метрика в каждом отчёте запуска; **очистка диска и удаление старых архивов запрещены
  без отдельного согласования** (ограничение этапа).

**Носитель расписания (не устанавливается сейчас):**
- вариант 1: **user crontab** пользователя `animastor` (уже есть, пуст; есть группа `docker` →
  `pg_dump`/`redis` доступны без root) — минимальное вмешательство;
- вариант 2: **systemd timer** (`OnCalendar=`, `Persistent=true`, `RandomizedDelaySec=`) —
  надёжнее (догонит после простоя), но установка unit требует root/согласования.
  Выбор — решение D4.
