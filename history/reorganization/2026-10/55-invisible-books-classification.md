## 5. План восстановления категории A (НЕ выполнялся)

Все 4 книги A имеют строку `books` → восстановление = **только материализация строк `scenes`** из канонического bundle. Не требуется создавать `books`, не требуется генерация.

**Примитив:** `scene-assets-repo.ensureSceneRow(bookId, chapterId, sceneId)` (`scene-assets-repo.js:362`) — `INSERT INTO scenes … ON CONFLICT (book_id, chapter_id, scene_id) DO NOTHING`. Пишет **исключительно** в `scenes`, ни в одну другую таблицу.

**Почему это безопасно для READY-assets:** `ensureSceneRow` не выполняет ни одного `UPDATE`/`DELETE` над `scene_assets` — 427 строк A1 (включая 15 READY) и файлы на диске остаются нетронутыми. Идемпотентно (повторный вызов = no-op, без дубликатов версий). Проверено тестом stage 53 (`orphan-books-diagnosis`: «сохранность READY-строк scene_assets после ensureSceneRow»).

**Процедура (на каждую книгу A, read-load → точечная запись `scenes`):**
1. Внутри контейнера (in-container, как probe stage 53): `bookLoader.loadBook(bookId)` → `book.collectScenes(loadedBook)` → список `(chapter_id, scene_id)` из канонического bundle.
2. Для каждой сцены: `sceneAssetsRepo.ensureSceneRow(bookId, ch, sc)` — **без** `resetScenes`, **без** `setDirtyUnitIds`, **без** dispatch. Только строка `scenes`.
   - A1: 5 сцен; A2/A3/A4: по 1 сцене.
3. **Идемпотентность:** `ON CONFLICT DO NOTHING` → повторный запуск безопасен, 0 дубликатов, не бампает версий.
4. **Сохранность READY:** никакого прикосновения к `scene_assets`/output. READY-строки и файлы не перезаписываются, не маркируются stale.
5. **A4 — предусловие:** сначала решение о guest-сессии (продлить `guests.expires_at` / конвертировать в постоянную), иначе purge (≤6 ч после 08:32) откатит восстановление. Без продления восстановление A4 **пропустить**.
