## 2. BACKUP TARGET — сравнение вариантов

### A. Существующее off-host хранилище (если доступно)

- **Статус: НЕ подтверждено.** Найден только GitHub по SSH (§1.4): пригоден
  **исключительно для git-репозиториев** (5 из 6; mono отсутствует).
  Для PG-дампа, `data/`, конфигов (содержит секреты) канала нет.
- **Требования:** endpoint владельца; учётки/ключ с доступом на запись;
  выбор канала (scp/rsync/облачное CLI — ничего не установлено → потребуется
  либо установка инструмента, либо чистый `ssh|cat`-стриминг); шифрование
  архива с секретами (`age`/`gpg` не установлены — либо ставить, либо
  транспортный канал обязан быть шифрованным); объём ≥0,7 ГБ на стороне.
- **Риски:** тайминг/пропускная способность; доверие каналу (секреты в
  `.env`-таре); моно-репозиторий не имеет удалённой копии вообще;
  восстановимость с целевого узла не проверена.
- **Необходимые решения:** подтвердить endpoint и учётки; определить,
  шифровать ли контент; разрешить ли push в GitHub (G8 — пока запрещён);
  включать ли mono-код в off-host и как (см. §4).

### B. Отдельный внешний диск/том (если подключение согласовано)

- **Статус: НЕ доступно сейчас** (второго носителя нет, §1.4); подключение
  возможно только по согласованию с владельцем (физический диск/блочный том).
- **Требования:** ёмкость ≥2 ГБ (пик 0,65 ГБ + запас); ФС и точка монтирования;
  владелец/права (`animastor`, 700 для каталога бэкапов); авто-монтирование
  не требуется (однократное окно); проверка `sha256` после записи.
- **Риски:** не подтверждён до момента подключения → GO/NO-GO по этому
  варианту невозможен заранее; риск монтирования поверх существующего пути;
  ФС без POSIX-прав (FAT/exFAT) сломает 600-права секретного тара →
  выбирать ext4/NTFS-с-оговоркой или шифровать архив.
- **Необходимые решения:** согласовать окно подключения; утвердить ёмкость и
  ФС; утвердить, что локальная копия остаётся временной и удаляется только
  отдельным разрешением (удаление сейчас запрещено).

### C. Временное локальное резервирование (только при доказанном запасе)

- **Статус: расчёт НЕ доказывает достаточность** под регламентный порог:
  запас над `15000000000` = 112 015 872 Б < 124 654 604 Б (минимум) и
  < 641 734 652 Б (абсолютный пик) → §1.3.
- **Требования (если всё же разрешено):** письменное решение владельца о
  временном снижении порога **либо** root `journalctl --vacuum-size=200M`
  (отдельное разрешение; даст ≈3 633 618 432 Б → свободно ≈18,7 ГБ, что
  закрывает и pull-гейт D0 16 600 000 000 Б).
- **Риски:** копии на том же диске, что источник, — **не защищают от отказа
  диска** (единственная ФС); превышение порога блокирует следующие фазы
  runbook; рост `opencode.db`/журнала съедает запас быстрее, чем планируется.
- **Необходимые решения:** vacuum-разрешение или пороговое исключение;
  обязательное последующее копирование off-host (A/B) до признания бэкапа
  завершённым.

### Сводная рекомендация

| Вариант | Доступен сейчас | Соответствует цели ( survivability ) | Вердикт |
|---|---|---|---|
| A. off-host (GitHub/endpoint) | только git, 5/6 репо; для данных — нет | да (для кода — да; для данных/конфигов — нет) | **требует решения владельца** (endpoint, учётки, шифрование) |
